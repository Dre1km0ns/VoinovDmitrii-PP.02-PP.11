## Проверка пересечений по времени

Два интервала [начало; окончание) одного столика в одну дату пересекаются, если начало существующей брони раньше окончания новой, а окончание существующей позже начала новой. Учитываются только брони в статусах «новая» и «подтверждена»: отменённые и отклонённые столик не занимают. Бронь, которая начинается ровно в момент окончания другой (например, 21:00 после брони до 21:00), пересечением не считается.

```
    def has_overlap(c, table_id, date, start, end):
        """Интервалы [start, end) пересекаются, если начало одного раньше конца другого и наоборот."""
        row = c.execute(
            "SELECT 1 FROM bookings WHERE table_id = ? AND date = ? "
            "AND status IN (?, ?) AND time_start < ? AND ? < time_end LIMIT 1",
            (table_id, date, *ACTIVE, end, start)).fetchone()
        return row is not None
```

При создании брони проверка выполняется внутри транзакции BEGIN IMMEDIATE: SQLite блокирует запись, поэтому два одновременных запроса не смогут забронировать один столик на одно время. Список свободных столиков строится тем же условием через NOT EXISTS и дополнительно отбирает столики, вместимость которых не меньше числа гостей.

## Проверка входных данных

**Таблица 6.1 — Ошибки API**

| Ситуация | Код | Сообщение |
|---|---|---|
| неверный формат даты или времени | 400 | Дата должна быть в формате ГГГГ-ММ-ДД / Поле start должно быть в формате ЧЧ:ММ |
| окончание не позже начала | 400 | Время окончания должно быть позже времени начала |
| гостей ноль или не число | 400 | Количество гостей должно быть больше нуля |
| пустое ФИО или неверный телефон | 400 | Укажите ФИО / Телефон должен быть в формате +7XXXXXXXXXX |
| гостей больше вместимости | 400 | Столик рассчитан на N гостей |
| столик или бронь не найдены | 404 | Столик не найден / Бронь не найдена |
| столик занят на это время | 409 | Столик уже забронирован на это время |
| повторная отмена | 409 | Бронь в статусе cancelled нельзя отменить |

Все запросы к базе параметризованные. Гость ищется по телефону: если он уже бронировал, новая бронь привязывается к существующей записи.

## Вывод

На этапе 2 на Flask сделан рабочий бэкенд бронирования поверх черновика базы данных, построенного по модели этапа 5 без её переделки. API выдаёт свободные столики на дату и интервал с учётом вместимости, создаёт брони с проверкой пересечений по времени в транзакции и отменяет их. Входные данные проверяются, ошибки возвращаются с понятными сообщениями и кодами 400, 404 и 409. Работа API проверена запросами. Веб-форма и отправка брони в беседу администраторов ВКонтакте — этап 3, официальный SQL-скрипт и защита базы — этапы 6–8.
